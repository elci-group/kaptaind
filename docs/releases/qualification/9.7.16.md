## 5. Container (`Dockerfile` → `kaptaind:stable-proof`)

- **Build:** `docker build` from the current source tree → `CONTAINER_EXIT=0` (316 MB image). First in-session attempt hit a transient Docker Hub DNS resolution failure fetching the `dockerfile:1` frontend; succeeded on retry once DNS recovered — environmental, not a build defect.
- **Runtime (honest):** a bare `docker run` exits cleanly (exit 0) because the runtime image intentionally contains no repository — the daemon requires a git repo at `/opt/kaptaind`. With a valid `kaptaind.toml` and a git repo mounted at `/opt/kaptaind`, the daemon starts, the health server binds `127.0.0.1:9090`, and `docker inspect` reports **`Health=healthy`**; `curl /health` returns `{"shark":null,"status":"ok","version":"9.7.16"}`. The full cluster→analyze→commit→push-gate loop runs in-container (push correctly blocked by branch protection), and the daemon stays healthy under it.
- **First-run note (roadmap §1.3):** operators must mount a repository into `/opt/kaptaind`; the image is a daemon runtime, not a self-contained demo. This is documented behaviour, not a defect, and is the basis for the containers PASS.

The full distro matrix (`ubuntu:24.04`, `debian:bookworm-slim`, `fedora:40`, `alpine:3.20`) and per-tier resource-cap runs (roadmap F1) are CI-provided; only the release image was built and exercised in-session.
